# Sprint 4 — Exit Gate, шаг 1: сквозной P&L через продукт

Этот файл фиксирует **один реальный продуктовый путь** и всё, что он вскрыл. Задача — не «позвать инструменты
скриптом», а провести запрос человека по всей цепочке:

```
user task → controller.analyze() → Agent Runtime (runAgent, без правок) → model/tool loop
          → Cell Tool Registry → createR7Bridge (поставочные тела) → CDP → ЖИВОЙ R7-редактор
          → реальное состояние книги → tool results → следующие шаги модели → final
```

## Дефект №1 (НАЙДЕН СКВОЗНОЙ СВЯЗКОЙ, ИСПРАВЛЕН `273d67c`)

**Классификация: НЕ дефект Runtime и НЕ protocol-following модели — дефект модельного описания инструмента.**

Сырые ответы модели (все четыре и последующие) — валидный JSON ровно нашего конверта, без markdown, и
`parseEnvelope` их **ПРИНИМАЛ**:

```
{"type":"tool_calls","calls":[{"tool":"list_sheets","arguments":{}},{"tool":"add_sheet","arguments":{"newName":"Допущения"}}]}
{"type":"tool_calls","calls":[{"tool":"write_range","arguments":{"sheet":"Допущения","address":"A1:B4","values":[[...]]}}]}
```

Ответ Runtime на такой вызов:

```
{"type":"tool_results","results":[{"tool":"batch","ok":false,"code":"TOOL_ERROR",
 "message":"one action per batch for a confirm tool; unknown tool name or invalid arguments"}]}
```

Причина доказана без модели (реальный каталог): схема `write_range` требует **`address` и `cells`**, а модель
отправила `values` → незнакомое свойство + отсутствующий обязательный → `TOOL_ERROR`. Модель **не могла узнать имя**:
единственное, что ей показывают, — `description`, а в нём были названы только **необязательный селектор**
(`sheet`/`sheetIndex`), но не обязательные аргументы.

**Измерено до фикса:** 3 из 7 Cell-инструментов требовали аргумент, которого нет в описании — `read_range`
(`address`), `write_range` (`address`, `cells`), `format_cells` (`address` + **десять** ключей форматирования);
у `add_sheet` не назван необязательный `name`. Это блокировало и запись чисел, и форматирование — то есть
собственную приёмку P&L.

**Следствие в прогоне:** `write_range` не исполнялся ни разу, модель повторяла тот же вызов ~117 раз до лимита
шагов (3 tool-call за 120 шагов — **не** нехватка лимита, `maxSteps` не поднимался).

**Фикс:** четыре описания называют свои аргументы; ничего больше не менялось — инструменты не добавлялись, схема не
расширялась, Runtime и протокол не тронуты, все описания в пределах 256 байт (205/248/247/164). Новый системный
тест обходит **весь** Cell-каталог и падает, если обязательный аргумент не назван в описании; отдельно закреплены
`write_range` (`address`/`cells`), `format_cells` (все ключи) и обязательность обоих написаний селектора.

## Дефект №2 (ОТДЕЛЬНЫЙ, НЕ СМЕШИВАТЬ С КАЛИБРОВКОЙ)

**`checkR7()` требует Word-редактор и потому на книге отвечает `R7_CHECK_UNAVAILABLE`.**

`src/ui/controller.js:446`: `if (platform?.editorType !== 'word' || typeof bridge?.probeCapabilities !== 'function')`
→ отказ; далее декодируется **шестибулевый Word-набор** (`api`, `getDocument`, `getDocumentId`,
`replaceTextSmart`, `getRangeBySelect`, `isTrackRevisions`).

Статус: **не блокирует прогон** (реестр строится независимо, `capabilityCount` просто остаётся `null`), поэтому
правится отдельно и не смешивается с калибровкой модели. Практическое следствие для пользователя: панель сообщает
«R7 недоступен» на исправной книге.

## Прочее, вскрытое прогоном

* контроллер по умолчанию **прикладывает выделение**, а чтение контекста требует Word-редактор → прогон на книге
  обрывался **до** модели; снимается тумблером панели (`setIncludeContext(false)`), это пользовательская настройка,
  а не правка Runtime;
* **кредит провайдера**: OpenRouter `60.0 / 60.18` — `gpt-4o × 4096 токенов` даёт 402; дешёвые модели проходят.
  Провайдер — настройка продукта, поэтому прогон идёт по здоровому маршруту, а DeepSeek остаётся **сравнительным**,
  протокол под него не подстраивается.

## Дефект №3 (ДОКАЗАН, ЖДЁТ ПОКАЗА ПЕРЕД ПРАВКОЙ RUNTIME-ТЕКСТА)

**Потолок «`actionsPerStep: 8` действий в одном шаге» не сказан модели НИГДЕ.**

* `src/shared/limits.js`: `AGENT_CEILINGS.actionsPerStep = 8`;
* в модельном системном тексте (`src/agent/runtime.js`, `systemRules`) этого ограничения нет — поиск не находит ни
  одного упоминания;
* превышение потолка даёт `PROTOCOL_ERROR`, который **сжигает единственный repair** прогона и завершает задачу.

Наблюдаемое следствие (сырые ответы Qwen, целевая семья продукта):

```
[0] {"type":"tool_calls","calls":[ add_sheet {name:"Допущения"},
      write_range {address:"A1:B3", cells:[[...]], sheet:"Допущения"}, add_sheet {name:"P&L"}, … ]}
    calls = 10   → parseEnvelope: REJECTED with PROTOCOL_ERROR
[1] … calls = 15 → parseEnvelope: REJECTED with PROTOCOL_ERROR   → прогон закончился на 2 шагах, 0 tool-call
```

То же, что и Дефект №1, но на слой выше: **жёсткое ограничение протокола, которое модель не может узнать**.
Qwen использует ПРАВИЛЬНЫЕ имена аргументов (`cells`, `name`) — то есть фикс описаний подтверждён независимо, —
но пакует 10–15 действий и упирается в неизвестный ему лимит.

Никаких правок Runtime до показа: предлагаемый минимальный фикс — **одна авторская строка в системном тексте**
(«не более 8 действий на шаг») плюс тест, читающий **содержание** модельного текста, чтобы правило нельзя было
потерять. Логика цикла, схемы и инструменты не меняются.

## Дефект №4 (НАЙДЕН ПОСЛЕ №1–№3, ИСПРАВЛЕН)

**`write_range` отправлял дробную строку как ТЕКСТ, поэтому числовой P&L был невозможен.**

Тело различало ровно два случая: целая строка → настоящее число; всё остальное → дословно. Дробная строка
попадала во «всё остальное», а этот движок хранит точечную дробь как **текст**. Отсюда `#VALUE!` во всех годах
P&L, который агент построил корректно (`= B2*(1+Допущения!B3)` умножало текст).

**Измерено нативно:**

```
Api.GetLocale()                        -> 1049 (ru-RU)      ← разделитель ЧИТАЕТСЯ, не предполагается
WRITE 0.15, 0.6                        -> ["POST_INSERT",1,2,1,1]   обе ячейки доказаны
read back                              -> [["0.15","0.6"]]
=ЕЧИСЛО(A1) / =ЕЧИСЛО(B1)              -> [["ИСТИНА","ИСТИНА"]]     движок подтверждает ЧИСЛА
WRITE =A1*2 , =A1+B1  → значения       -> [["0.3","0.75"]]          формулы СЧИТАЮТСЯ
WRITE 1.0, 2.50, 100.00                -> ["POST_INSERT",1,3,1,1,1] trailing zeros доказаны (три флага)
read back                              -> [["1","2.5","100"]]      каноническая запись числа
WRITE 0.1234567890123456789            -> ["POST_INSERT",1,1,1]     длинная дробь — число, капа нет
WRITE =A1*3                            -> 3
```

**Набор локалей — явный, а не «1049, иначе точка»:** запятая как десятичный разделитель принята в de-DE (1031),
fr-FR (1036), es-ES (1034), it-IT (1040), pt-BR (1046), pl-PL (1045), tr-TR (1055), cs-CZ (1029), uk-UA (1058) и
др., и набор перечислен В ТЕЛЕ. Локаль вне набора получает точку — ровно то поведение, что было до появления
дробного маршрута, — и **числовое доказательство для неё не применяется**: значение доказывается написанием.
Иначе говоря, неизвестная локаль может потерять раунд-трип, но не может быть обманута утверждением «текстовая
ячейка — это число».

**Предел доказательства (честно, а не подразумеваемо).** Чтение из ячейки — это СТРОКА, в ней нет типа. Поэтому
числовое доказательство требует **канонической записи** разобранного значения (благодаря чему `' '`, `'0x10'`,
`'1e1'` отвергаются) и применяется **только к тем маршрутам, которые тело выбрало само**. Остаточный случай,
который оно различить НЕ может: текстовая ячейка, чья запись совпадает с канонической записью числа (`'0.15'`
— это и число, и такая строка). Это цена того, что `'1.0'` вообще доказывается, и она записана здесь, а не
скрыта за формулировкой.

**Что СОЗНАТЕЛЬНО остаётся текстом** (и потому формула, их потребляющая, всё ещё может дать `#VALUE!`):
`'.5'`, `'+0.15'`, `'00.15'`, `'1e3'`, `'1.'`, `'000.5'`, `'1 000.5'`, ведущие/хвостовые пробелы,
`'NaN'`, `'Infinity'`, полноширинные и арабо-индийские цифры, а также дробь с целой частью длиннее 15 цифр
(её числовая запись была бы потерей точности — измерено на 20-значном целом: `'…7890'` читается как `'…67000'`).

**Что именно изменено:** третий **закрытый** маршрут в теле — дробь по шаблону
`/^-?(0|[1-9][0-9]{0,14})\.[0-9]+$/` отправляется в локальной числовой форме через **границу параметра**
(`decimalInLocale`, как `normalize`/`startsWithEquals`), разделитель берётся у движка (`Api.GetLocale()`), а
доказательство для числового запроса стало **числовым**: движок печатает сохранённое число канонически, поэтому
`'1.0'` возвращается как `'1'`. Схема, Runtime, protocol и validator не тронуты; целая ветка, дословная ветка и
формульный путь сохранены; `'007'` и прочие fail-safe случаи не изменились.

**Отклонённое первое исправление (честно).** Первая версия сравнивала **написание** и тем самым (а) ломала
`'1.0'`, `'2.50'`, `'100.00'` — верно записанное число объявлялось недоказанным → `UNCERTAIN` со удержанным слотом,
и (б) могла «доказать» текстовую ячейку. Независимое ревью нашло это до коммита; исправление — числовое
доказательство, отсутствие капа на дробную часть и разделитель из локали. Стенд теперь **моделирует движок**
(канонические числа + измеренная локаль), а не только эхо аргумента, — ровно та слепота, из-за которой блокер был
невидим.

## Приёмка шага 1 (Exit Gate): P&L на реальном продуктовом пути

Прогон 14: `qwen/qwen3.8-27b`, тот же промпт и те же лимиты, 41 шаг, 9 tool-call, статус `TIMEOUT` (агент
продолжал полировать уже готовую работу и упёрся в хостовый дедлайн прогона — **работа к тому моменту сделана**).
Книга после прогона, прочитанная **поставочными телами** и пересчитанная **независимым проверяльщиком**:

```
Допущения: выручка за год 1 = 10 000 000 · годовой рост = 0.15 · себестоимость, % = 0.6

P&L          Год 1        Год 2         Год 3
Выручка      10000000     11500000      13224999.999999998
Себестоимость 6000000      6900000       7934999.999999998
Валовая       4000000      4600000       5290000
Маржа               0.4          0.4             0.4000000000000001

формулы: = Допущения!B2 · = B2*(1+Допущения!B3) · = C2*(1+Допущения!B3)
         = B2*Допущения!B4 · = C2*Допущения!B4 · = D2*Допущения!B4
         = B2-B3 · = C2-C3 · = D2-D3        = B4/B2 · = C4/C2 · = D4/D2
```

Проверяльщик (`verify-pnl.mjs`, считает арифметику САМ, не доверяя отчёту агента): **ACCEPTANCE: PASS**, 15 из 15:

* отдельный лист допущений; исходные значения; отдельный лист P&L; все четыре показателя;
* **межлистовые ссылки** использованы (ссылки на «Допущения»);
* **ни одного `#`-значения ошибки** (было `#VALUE!` во всех годах до Дефекта №4);
* валовая = выручка − затраты для каждого года (4 000 000 / 4 600 000 / 5 290 000 — совпало с пересчётом);
* маржа = валовая / выручка для каждого года (0.4 / 0.4 / 0.4 — совпало);
* движок сам подтверждает, что допущение — **число** (`=ЕЧИСЛО(Допущения!B3)` → `ИСТИНА`).

Плюс форматирование исполнено агентом (`format_cells` ×3 — числовой/процентный/денежный форматы из задачи) и
агент **сам прочитал результат** (`read_range` ×2 — его самопроверка), то есть сквозной путь
«задача → Runtime → модель → реестр → мост → поставочные тела → живая книга → результаты → следующие шаги»
пройден до конца.


**Вывод по калибровке.** Дефект №3 закрыт: Qwen-72B перестал выдавать 10–15 вызовов, qwen3.8-flash держит 1–2
вызова в шаге. Дефект №1 подтверждён независимо: Qwen использует ровно те имена, которые появились в описаниях
(`cells`, `name`). Полный P&L на Qwen пока не доведён, и это **не** дефект инструментов:
* аккаунт OpenRouter исчерпан (`60.19 / 60.0`) — середина длинного прогона обрывается `HTTP_ERROR`;
* 72B не укладывается в минимальный таймаут;
* у qwen3.8-flash в полном прогоне на 4-м шаге `PROTOCOL_ERROR`, который **не воспроизведён в перехвате**
  (в перехвате все ответы валидны) — прежде чем что-то менять, нужно поймать именно этот конверт.

**Новое наблюдение того же класса, что №1/№3** (пока не оформлено дефектом): модель зовёт `read_sheet` с
аргументом `sheet`, хотя по конструкции T5.3a у `read_sheet` аргументов нет; описание говорит «активный лист», но
прямо не говорит «аргументов не принимает».
