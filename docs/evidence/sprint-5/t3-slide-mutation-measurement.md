# Sprint 5, T3 — измеренная поверхность перед контрактом (2026-10-07)

**Зачем.** Контракт T3 (§13 плана) обязан опираться на измерение, а не на догадку. Часть замеров T1 **не
воспроизвелась** на живой колоде, а часть нужных фактов T1 вообще не различал. Ниже — то, что установлено
заново на целевом стенде, и то, чего эти замеры НЕ показывают.

**Стенд.** Astra Linux SE 1.7.9.41 + Р7-Офис **2026.1.2-1942~astra-signed** (целевой билд), живой редактор
презентации, одноразовая колода (5 слайдов), плагин открыт штатным вендорским путём, тела исполнены через
`Asc.plugin.callCommand`. Поставочный `panel.js` — `a52643c1…`. Windows-прогон подтверждает те же факты в
приёмке T3.

## 1. Создание слайда и наследование layout

| факт | измерение |
| --- | --- |
| `Api.AddSlide(sourceSlide.GetLayout())` | создаёт слайд (`5 → 6`), `classType='slide'`, новый слайд становится текущим |
| **аргумент layout у `AddSlide` ИГНОРИРУЕТСЯ** | при текущем слайде 0 (layout `"306"`) и источнике — слайде 2 (layout `"219"`) созданный слайд получил **`"306"`**, то есть layout **текущего** слайда: `AddSlideHonouredTheNamedLayout=false`, `createdInheritedCurrentLayout=true` |
| **`created.ApplyLayout(sourceLayout)` — это и есть выбор layout** | после вызова созданный слайд имеет **`"219"`** = layout названного источника (`equalsSource=true`), счётчик остаётся `6` (слайд не добавляется) |
| позиция нового слайда | вставляется рядом с **текущим** и становится текущим: текущий 0 → создан 1; текущий 1 → создан 2 |
| свежий слайд | уже содержит **два** placeholder-объекта (`classType='shape'`, `GetPlaceholder()` истинно), у каждого 1 пустой абзац |
| колода несёт **два** layout | `{"id":"306","master":"101"}` (11 200 симв. в строке) на слайдах 0/1/3 и `{"id":"219","master":"101"}` (10 552) на 2/4 |

> **Исправление к первой редакции этого файла (2026-10-07, после нативной приёмки T3).** Первая редакция
> утверждала, что `Api.AddSlide(sourceSlide.GetLayout())` наследует **именно переданный** layout, и ссылалась на
> прогон «источник — слайд 3». Тот прогон был **неразличающим**: у слайда 3 и у текущего слайда 0 был **один и
> тот же** layout (`"306"`), поэтому сравнение не могло отличить «переданный layout» от «layout текущего
> слайда». Замер на источнике с **другим** layout (слайд 2, `"219"`) показал правду: `AddSlide` аргумент
> игнорирует, а выбирает layout `ApplyLayout`.

**Ловушка идентичности layout (уточнено 2026-10-07 после нативной приёмки T3).**
`slide.GetLayout().ToJSON()` возвращает **СТРОКУ JSON**, а не объект: измерено
`Object.prototype.toString.call(json)` = `[object String]`, длина строки **11 200**, а её содержимое начинается с
`{"id":"306","master":"101",…}`. Поэтому:
* у результата **нет свойства `.id`** вообще (первая редакция этого файла ошибочно называла его объектом без
  собственного `id` — эта ошибка ушла в unit-ригу и стоила отдельного fix-round);
* `JSON.stringify(json)` над строкой даёт **экранированную** строку (`"{\"id\":\"306\",…}"`) — сравнивать надо
  сами значения, а не их повторную сериализацию;
* единственная надёжная идентичность — **сама строка**; её и сравнивает доказательство наследования;
* из неё же честно извлекается `"id"` как **строка** (`"306"`), а не как число.

## 2. Запись текста: T1-маршрут не воспроизвёлся, найден работающий

| маршрут | результат |
| --- | --- |
| `AddText` на абзац ДО присоединения (`CreateParagraph` → `AddText` → `AddElement`) | текст **пуст** (`after=[""]`) |
| `AddText` на ссылку, сохранённую ДО присоединения | текст **пуст** (`after=[""]`) |
| `shape.SetText(...)` | метода **нет** (в объекте shape 22 имени, `SetText` отсутствует) |
| `content.GetElement(0).AddText(text)` на существующем абзаце | **работает** (`after=["T3_ROUTE_PROBE"]`) |
| **`RemoveAllElements()` → `AddElement(Api.CreateParagraph())` → `content.GetElement(0).AddText(text)`** | **работает**, в т.ч. кириллица (`after=["Текст для проверки"]`) |

**Причина отказов:** текст живёт на **элементе (абзаце)**, а не на контенте, и обёртка, взятая до
присоединения, **не та же самая**, что `GetElement(0)` после него (тождество обёрток нестабильно — тот же класс,
что измерен в §12.4 отчёта T2). Поэтому запись обязана брать элемент **повторно, по индексу, ПОСЛЕ**
`AddElement`, и доказательство — тоже.

## 3. Undo: пользовательский маршрут существует, но он editor-side

| где вызвано | маршрут | откат мутации плагина |
| --- | --- | --- |
| plugin-фрейм, **тот же** `callCommand` | `Api.Undo()` / `logicdoc.Document_Undo()` | **да** (`6→7→6`, `5→6→5`) |
| plugin-фрейм, **отдельный** вызов | `Api.Undo()` | **нет** (6 осталось 6) |
| plugin-фрейм, **отдельный** вызов | `logicdoc.Document_Undo()` | **нет** (6 осталось 6) |
| plugin-фрейм, отдельный вызов | `Api.asc_undoAllChanges()` | **да**, но стирает **всю** историю (`canUndoAfter=false`) |
| **фрейм редактора**, хост-объект | `g_asc_plugins.api.Undo()` | **нет** (6 осталось 6) |
| **фрейм редактора**, хост-объект | **`g_asc_plugins.api.WordControl.m_oLogicDocument.Document_Undo()`** | **ДА: `6 → 5`**, подтверждено независимым чтением из plugin-фрейма |

**Вывод:** откат мутации, сделанной плагином, возможен — но маршрут принадлежит **редактору**
(`Document_Undo()` на его собственном экземпляре API), а не плагину: из плагина между вызовами точечные
маршруты не действуют. Именно этот маршрут становится приёмочным критерием undo для каждой мутации T3 (§13.5).

`asc_getCanUndo()` во всех прогонах был `true` — то есть редактор считает, что откатывать есть что, даже когда
вызов из плагина ничего не меняет.

## 4. Чего эти замеры НЕ показывают

* **Ctrl+Z в интерфейсе редактора не подтверждён.** Синтетическая клавиша, отправленная через CDP в
  page-target (и после `window.focus()` во фрейме редактора, и при закрытом плагине), мутацию **не откатила**;
  но доставка клавиши в CEF-фрейм редактора этим способом не доказана, поэтому «UI-undo не работает» —
  **недоказанное утверждение**, и оно здесь не делается. Доказан только API-маршрут §3.
* Не проверено, восстанавливает ли откат **индекс текущего слайда** так, как его ожидает пользователь.
* Не проверено поведение `Redo()` и парность undo/redo.
* Не проверено, откатывает ли **каждую** мутацию T3 один и тот же маршрут: §13.5 требует доказывать это
  **по каждой** мутации в её собственной приёмке.
* Не проверено, помечает ли откат документ «изменённым» (грязный флаг/сохранение).
