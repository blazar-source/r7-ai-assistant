# Sprint 5, T3 — native evidence: `add_slide` + `set_slide_text` (2026-10-07)

**ЦЕЛЬ.** Подтвердить на живых редакторах, что **поставочные** тела T3 создают слайд на существующем layout и
пишут текст, что их доказательства конечного состояния проходят, и что **каждую** мутацию можно откатить
штатным маршрутом редактора (критерий владельца, §13.5 плана).

**ЧТО ИСПОЛНЯЛОСЬ.** Тело извлекается **из поставочного** `dist/plugin/panel.js` генератором
`t3-native-proof.mjs` (единственная нога `slidemutate`, несущая `Api.AddSlide` + `RemoveAllElements`, 9 142
символа) и исполняется в фрейме плагина живого редактора. Рядом те же объекты читаются **независимо**
плагин-фреймом и фреймом редактора. Ничего не сохранялось; колода одноразовая.

**СТЕНДЫ.** Astra Linux SE 1.7.9.41 + Р7-Офис **2026.1.2-1942~astra-signed** (целевой) и **Windows R7-Office
Editors 2026.3.1**. Поставочный `panel.js` на обоих — один и тот же (`42c62aff…` в этом прогоне).

## 1. `add_slide`: создание на НАЗВАННОМ layout (обе площадки совпали)

Запрос: `layoutFromSlideIndex: 2` при текущем слайде 0 (у слайда 2 **другой** layout — `"219"`, у текущего
`"306"`).

| проверка | Astra | Windows |
| --- | --- | --- |
| ответ тела | `[1, 6, 1, "219", 1]` | `[1, 6, 1, "219", 1]` |
| число слайдов до → после | 5 → 6 | 5 → 6 |
| созданный слайд | индекс 1, current = 1 | идентично |
| **layout созданного слайда** | **`"219"`** = layout названного источника | идентично |
| `layoutPreserved` | `1` (истина) | идентично |
| независимое чтение | слайд 1 несёт layout `219`, слайды 0/2… `306` | идентично |
| источник вне диапазона (`99`) | `[0,"TOOL_ERROR"]` | идентично |
| запрос без `mode` | `[0,"CAPABILITY_UNAVAILABLE"]` | идентично |

**Почему это не «случайно совпало».** `Api.AddSlide(x)` **игнорирует** `x` и даёт новому слайду layout
**текущего** слайда; layout выбирает `created.ApplyLayout(sourceLayout)` (измерено отдельно:
`AddSlideHonouredTheNamedLayout=false`, затем `ApplyLayout` → `"219"`, счётчик не растёт). Поэтому ответ
`[1,6,1,"219",1]` доказывает, что в теле реально отработал шаг `ApplyLayout`: без него доказательство не
проходит и тело честно отвечает `[1,"APPLY_UNCERTAIN"]` — что и наблюдалось в приёмке до fix round 2.

## 2. `set_slide_text`: запись целого текста объекта (обе площадки совпали)

Запрос: текущий слайд, `objectOrdinal: 0`, текст `T3_NATIVE_PROOF`.

| проверка | Astra | Windows |
| --- | --- | --- |
| ответ тела | `[2, 1, 0, 15, 15]` | `[2, 0, 0, 15, 15]` (индекс текущего слайда отличался, потому что до этого откатывали создание) |
| независимое чтение | текст объекта 0 = `T3_NATIVE_PROOF`, объект 1 пуст | идентично |
| повторная запись того же текста (idempotent success) | `[2, …, 15, 15]` | идентично |
| кириллица | `[2, …, 18, 34]` — 18 символов, **34 байта** UTF-8 | идентично |
| несуществующий ordinal (`99`) | `[0,"TOOL_ERROR"]` | идентично |
| несуществующий индекс слайда (`99`) | `[0,"TOOL_ERROR"]` | идентично |
| текст сверх лимита | тело принимает (граница объявлена на слое инструмента) | идентично |

**Почему маршрут именно такой.** Текст живёт на **элементе** контента, и ссылку надо брать **после**
присоединения: `RemoveAllElements()` → `AddElement(Api.CreateParagraph())` → `AddText` на
**повторно полученном** `GetElement(0)`. Запись на неприсоединённый абзац (или на ссылку, сохранённую до
присоединения) оставляет текст пустым — измерено отдельно (§2 файла
`t3-slide-mutation-measurement.md`), и именно это проверяет unit-рига.

## 3. Native Undo по КАЖДОЙ мутации (критерий владельца, §13.5) — ВЫПОЛНЕН

Маршрут: `g_asc_plugins.api.WordControl.m_oLogicDocument.Document_Undo()` из фрейма **редактора** (не из
плагина: из плагина между вызовами точечные маршруты не действуют). После каждой мутации вызвано до 5 undo с
независимым чтением **после каждого** вызова.

| мутация | шагов до возврата | что доказано |
| --- | --- | --- |
| `add_slide` | **4** (после #4 число слайдов 5, current 0) | состояние **точно** как до мутации; промежуточные шаги документ не ломают |
| `set_slide_text` | **4** (после #4 текст объекта снова `""`) | текст возвращён точно к прежнему |

Astra и Windows совпали и здесь: **4** шага в обоих случаях.

**Глубина undo и группировка (ответ на открытый вопрос §10.7).** Измерены варианты на той же
последовательности операций движка:

| вариант | шагов undo |
| --- | --- |
| как в поставочном теле (без группировки) | **4** |
| `presentation.CreateNewHistoryPoint()` перед мутацией | **2** (и `asc_getCanUndo()` → `false` после исчерпания) |
| `Api.setStartPointHistory()` + `Api.setEndPointHistory()` вокруг мутации | **2** |
| `CreateNewHistoryPoint()` вместе с start/end | **2** |
| **1 шаг** | **не достигнут ни одной измеренной комбинацией** |

Все четыре примитива существуют на обеих сборках. Поставочные тела **намеренно не вызывают** эти примитивы:
они меняют структуру истории документа пользователя, а этого план T3 не предписывал. Зафиксированный факт:
мутация **откатывается** штатным маршрутом и сходится точно, но **не за одно нажатие**; если продукту нужен
одношаговый откат, это отдельное решение владельца (§13.5, §10.7), и лучший измеренный вариант даёт 2 шага.

## 4. Чего этот прогон НЕ показывает

* **Одношаговый undo** не достигнут (см. §3) — это измеренный факт, а не «доделка».
* **Ctrl+Z в интерфейсе** не проверялся: синтетическая клавиша через CDP в фрейм редактора не доказана;
  проверен **API-маршрут** редактора, а не UI-жест.
* **Текст сверх лимита**: тело границу не отсекает (её держит слой инструмента, который до моста не
  доходит). Это ожидаемое разделение, но нативным прогоном проверено именно поведение тела.
* **Сохранение файла** и повторное открытие (Save/reopen из exit gate) — это шаг exit gate, не T3.
* **Незатронутость остальных слайдов** после переработки — предмет T5 (в T3 проверялось только, что чтение
  остальных слайдов не изменилось в ходе этих операций).
* Колода несёт два layout; **выбор произвольного layout, не привязанного к существующему слайду**, не
  проверялся — такого глобального списка на поверхности нет (§12.7).
