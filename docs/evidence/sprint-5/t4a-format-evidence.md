# Sprint 5, T4a — native evidence: `format_slide_text` (2026-10-07)

**ЦЕЛЬ.** Подтвердить на живых редакторах, что **поставочное** тело форматирования применяет запрошенные
свойства, **доказывает** их чтением документа, отказывает до мутации на некорректный запрос, и что мутацию
можно откатить штатным маршрутом редактора.

**ЧТО ИСПОЛНЯЛОСЬ.** Тело извлекается из поставочного `dist/plugin/panel.js` (`slideformat`-нога, генератор
`t4-native-proof.mjs`) и исполняется в фрейме плагина. Независимый читатель разбирает `rPr` из
`content.ToJSON()` — то есть читает **сам документ**, а не ответ тела. Доказательство формата — по
`docs/evidence/sprint-5/t4-slide-mutation-measurement.md`.

**СТЕНДЫ.** Astra SE 1.7.9.41 + Р7 **2026.1.2-1942** (целевой) и **Windows R7-Office Editors 2026.3.1**;
поставочный `panel.js` — `d7393523…` в этом прогоне; одноразовая колода, ничего не сохранялось.

## 1. Успешный путь и отказы

| запрос | Astra | Windows | что доказано |
| --- | --- | --- | --- |
| шесть свойств (`bold, italic, underline, fontSize 28, fontFamily Arial, color 255,0,0`) | `[3, 0, 0, 17, bold, italic, underline, fontSize, fontFamily, color]` | `[1, 'APPLY_UNCERTAIN']` на ПЕРВОМ вызове, успех на повторном | см. §3 — расхождение по `fontFamily` |
| только `fontSize: 12` | успех | успех | `SetFontSize(24)` → `rPr.sz = 1200` = 12 pt |
| без свойств | `[0, 'TOOL_ERROR']` | идентично | отказ **до** мутации |
| неизвестное свойство | `[0, 'TOOL_ERROR']` | идентично | закрытый набор ключей |
| `fontSize: 400` | `[0, 'TOOL_ERROR']` | идентично | граница проверена ДО диспатча |
| `color.r: 300` | `[0, 'TOOL_ERROR']` | идентично | граница проверена ДО диспатча |
| несуществующий `objectOrdinal` | `[0, 'TOOL_ERROR']` | идентично | адресация доказана |

Независимое чтение после успешного вызова (Windows): `rPr = {"sz":2800,"i":true,"b":true,"u":"sng",
uniFill…"rgba":{"red":255,"green":0,"blue":0,"alpha":255}, "latin":"Arial","cs":"Arial"}` — то есть **все**
запрошенные свойства реально в документе, а `sz:2800` = 28 pt.

## 2. Два дефекта, найденных приёмкой, и их исправление

1. **Границы не проверялись до диспатча.** Первая версия тела ДИСПАТЧИЛА мутацию при `fontSize: 400`
   (движок реально записал `sz: 20000`) и при `color.r: 300`, а запрос без свойств/с неизвестным свойством
   возвращал 4-элементный «успех», который декодер превращал в неопределённость. Исправлено: закрытый набор
   ключей, «хотя бы одно свойство», границы `fontSize 1..scope.maxFontSize` и компоненты цвета `0..255` —
   всё как `[0, 'TOOL_ERROR']` **до** любого сеттера.
2. **Единицы размера шрифта.** Тело вызывало `SetFontSize(fontSize)`, а движок трактует аргумент как
   **полупункты**: измерено `SetFontSize(2)→sz 100`, `(12)→600`, `(28)→1400`, `(56)→2800`. Поэтому запрос 28 pt
   давал 14 pt и доказательство не сходилось. Исправлено: вызов `SetFontSize(fontSize * 2)`, ожидание
   `sz === fontSize * 100`; рига моделирует `argument × 50`.

Оба дефекта видел **только** нативный прогон: unit-рига моделировала то, что тело ожидало, а не то, что делает
движок.

## 3. Измеренное расхождение Astra ↔ Windows: `fontFamily`

| чтение внутри того же вызова | Astra | Windows |
| --- | --- | --- |
| `content.ToJSON()` → `rPr.latin`/`cs` после `SetFontFamily('Arial')` | **`"Arial"`** | **`undefined`** (три последовательных чтения — то же) |
| `slide.ToJSON()` (34 732 символа) — поиск `Arial` | найден | **не найден**, `latin` остаётся темой `+mn-lt` |
| видно ли семейство в СЛЕДУЮЩЕМ вызове | да | **да** (следующая команда его уже видит) |

**Следствие:** на целевом стенде Astra `fontFamily` доказуем внутри вызова; на Windows он применяется, но
внутри вызова **не наблюдаем ни одним измеренным маршрутом**, поэтому тело честно отвечает
`APPLY_UNCERTAIN` (требование §6.0.5: недоказуемость после диспатча — неопределённость, без повторов).
Смягчать это утверждением «применилось» нельзя — это было бы доказательство без доказательства.

**Решение контроллера (Ruling):** `fontFamily` **остаётся** в контракте. Основание — §0 плана: источник истины
по compatibility это **Astra**, Windows — дополнительный стенд, а расхождение фиксируется как факт. Цена, если
решение неверно: на Windows запрос, включающий `fontFamily`, будет давать `TOOL_UNCERTAIN`; чтобы этого
избежать, свойство нужно либо убрать из контракта, либо найти не измеренный пока маршрут чтения — и то и другое
ограничено одной ногой и не затрагивает остальные свойства.

## 4. Undo — критерий приёмки мутации

Маршрут: `g_asc_plugins.api.WordControl.m_oLogicDocument.Document_Undo()` из фрейма редактора, до 10 вызовов с
независимым чтением после каждого.

| сценарий | результат |
| --- | --- |
| форматирование абзаца, **существовавшего** в загруженном документе | `rPr` с `{"b":true,…}` возвращается к `{"bFromDocument":false,…}` — **откатывается** |
| реалистичный сценарий: плагин записал текст, затем отформатировал его | после исчерпания истории текст снова пуст, `rPr` снова чистый — **видимое состояние возвращается точно** |

Глубина: точечный откат форматирования требует нескольких вызовов undo, и после исчерпания истории
`asc_getCanUndo()` становится `false`; `CreateNewHistoryPoint()` картину не меняет. Это тот же класс, что
измерен в T3 (§13.5): маршрут редактора работает, но не за одно нажатие.

## 5. Чего этот прогон НЕ показывает

* **Визуальный результат** форматирования не проверялся: доказано, что свойства записаны в `rPr`, а не то, как
  это выглядит на слайде.
* `SetSpacing` и `SetHighlight` остаются проверенными только на существование (в контракт T4a не входят).
* Расхождение по `fontFamily` измерено на двух сборках; на **третьей** сборке его поведение неизвестно.
* Undo проверен для форматирования; откат таблиц/картинок — предмет T4b.
* Позиция/размер объекта и содержимое ячеек — вне T4a.
