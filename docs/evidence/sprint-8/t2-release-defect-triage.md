A “must measure” item is not pre-labelled a defect. If the measurement exposes failure or cannot bind required acceptance to the final bytes, it becomes a blocker under the contract.

## Recommended measurement order

1. After T6 version/docs changes and any blocker-only repairs are committed, pin the candidate release commit and build ZIP/DEB/SBOM/checksums.
2. Verify archive/SBOM/inventory independently, then measure plugin-ZIP lifecycle and DEB install/activation on the exact hashes.
3. Run target-native Word, Cell and Slide journeys; observe mounted-panel terminal state, policies/Preview where applicable, Undo and cleanup. Treat semantic behavior and file/state invariants as primary; pixel captures are supporting evidence.
4. Run security review and the repeat-build/final reconciliation. If any commit follows, restart the artifact-identity step because ZIP provenance changes.

## Concerns for later tasks

* The release contract currently selects `dist/SHA256SUMS`; T7 must keep that name or explicitly reconcile a replacement before producing final evidence.
* The RC's separately distributed ZIP cannot remain in the artifact list with only DEB lifecycle evidence.
* Do not confuse controlled/provider `TIMEOUT` or `HTTP_ERROR` with a product defect without evidence of unsafe or misleading handling; equally, do not call a failed real-model request a successful model calibration.
* Do not import the test-only `.1` fixture into release instructions or infer future-upgrade safety from it.
* Every later commit changes the provenance-bearing ZIP identity even when DEB payload bytes happen not to change.
