## 2. Что реализовано в этой стадии

**Word Tool Layer (13 пунктов каталога разрешены):**
- чтение: `read_document_text`, `read_paragraph`, `find_text`, `read_structure` (+ ранее `read_selection`; `read_context` изъят политикой `deny`);
- мутации: `insert_blocks`, `insert_table`, `set_heading`, `format_range`, `add_hyperlink`, `replace_text`, `insert_image`, `insert_comment`
  (плюс уже существовавшие `insert_paragraph`, `replace_selection`);
- `create_list` — **честно исключён**: девять публичных форм в двух раундах не создают нумерованный/маркированный абзац на этой сборке (`GetAllNumberedParagraphs()` = 0, маркеров в экспорте нет, `GetParaPr().SetNumbering` не существует).

**Оркестрация длинных документов (Plan → Execute → Verify → Continue):**
- профиль `bulk` в реестре: модель видит **пять** инструментов (`read_document_text`, `read_structure`, `insert_blocks`, `insert_table`, `format_range`); `insert_paragraph` и другие позиционно-зависимые **не показываются**; сам реестр и tools не тронуты — фильтруется только model-visible каталог (`catalogue()`/`resolve` хранят всё);
- подсказки инструментов: у всех 16 дескрипторов есть авторское назначение (≤256 байт), оно доходит до модели;
- confirm-инструменты скрыты из списка для модели, но остаются разрешаемыми → путь предпросмотра/применения панели цел;
- оркестратор в панели: план-проход (только план, в разбираемом виде `РАЗДЕЛЫ/ОБЪЁМ/ТАБЛИЦЫ/ЗАКЛЮЧЕНИЕ`) → до **12** проходов исполнения → **самостоятельная** проверка документа (структура + объём) → точный перечень недостающего в следующий запрос → `complete` только при пустом списке; `TOOL_UNCERTAIN` завершает прогон **без автоповтора**;
- пороги поднимаются из самого запроса (таблицы → ≥2; выводы → обязательны; «~10 страниц» → 18 000 знаков), критерии = максимум(порог, план), план не может занизить порог;
- лимиты задач: `AGENT_GUARDRAILS` = 120 шагов / 400 вызовов / 30 минут (конфигурацией, без правок логики рантайма); хост-дедлайн прогона 1 950 000 мс.

**Изменения в `src/agent/` за стадию — ровно одно место:** модельный проброс в `runtime.js` (описания + список без confirm). Цикл, валидация, guardrails, confirm-ветка и обработка ошибок не менялись.

## 3. Что проверено на реальном R7 / Astra (2026.1.2.1942)

Все мутации проверены **независимым чтением документа**, а не отчётом инструмента:

| Инструмент | Проверка на цели |
|---|---|
| `insert_blocks` | глава в конец, точная дельта (+2 абзаца / +1 заголовок), в т.ч. при совпадающих текстах; **многострочный блок теперь подтверждается** (фикс `11165fd`) |
| `insert_table` | 1×2 и 3×5 (15 ячеек), порядок таблиц совпадает с `Push`; чужая форма → закрытый отказ без записи |
| `set_heading` | уровень 2, «дубликат текста» → изменился именно адресованный объект, «уже заголовок» → отказ без записи |
| `format_range` | выравнивание + жирный/курсив/подчёркивание/зачёркивание, **вложенные** маркеры, необязательное `align` |
| `add_hyperlink` | ссылка в указанный абзац; независимо измерено элементное чтение (`GetClassType()='hyperlink'`, `GetLinkedText()`, `GetDisplayedText()`) |
| `replace_text` | заменены **оба** вхождения, точная арифметика (2 → 0, замен 2), контроль не тронут |
| `insert_image` | абзацев +1, `GetAllImages()` 0 → 1, `GetAllDrawingObjects()` 1, markdown содержит точный `![](data:...)` |
| `insert_comment` | комментариев 0 → 1, текст и id совпали с отчётом инструмента |

**Свободный длинный запрос** (дословно «создай структурированный документ примерно на 10 страниц, добавь главы, несколько таблиц, списки, выводы и оформи его», без подсказок инструментов), лучший измеренный прогон: **187 абзацев, 11 заголовков, 6 таблиц, ≈11 900 знаков (≈5–7 страниц)**, действия — только `insert_blocks`/`insert_table`/чтения.

Уроки платформы (измерены, лежат в памяти и в журнале): `doc.Push` добавляет в конец, `InsertContent` — в начало (и может затереть текст ✗); `Api.CreateTable(a,b)` = **a столбцов × b строк**; `paragraph.GetRange` — относительно абзаца, `doc.GetRange(a,b)` — глобальные позиции документа; `ToHtml()` экранирует теги, markdown — нет; `ToMarkdown(второй аргумент = true)` **убирает** base64 картинки; редактор хранит `\n`/`\r\n` как `\r`; объектной идентичности между `GetAllParagraphs()` и `GetAllHeadingParagraphs()` **нет**; `replace_selection` в цикле — предложение (реальный путь — Apply в панели); сборка R7 не сохраняет открытый документ на диск.

## 4. PASS / PARTIAL / known limitations

**PASS:** Word Tool Layer; bulk-профиль (неправильное использование `insert_paragraph` устранено); Plan → Execute → Verify → Continue; 5–7 страниц за свободный запрос; таблицы и структурированный документ; `TOOL_UNCERTAIN` безопасно останавливает запись без повтора.

**PARTIAL:** воспроизводимость результата модели — объём и число таблиц варьируются от прогона к прогону (достигнутый критерий приёмки «3 × ≥18 000 знаков с ≥2 таблицами» **не** выполнен: получено ≈5–12 тыс. знаков и 0–6 таблиц). По решению владельца это **вынесено за good-enough scope** (см. §5), а не является блокером.

**Known limitations (не блокеры):**
1. **Списки**: рабочей публичной формы нумерации нет; списки — обычные абзацы (в bulk-прогонах модель импровизирует маркерами `- ` внутри абзаца).
2. **Позиционно-зависимые инструменты** (`insert_paragraph`, `set_heading`, ссылки, картинки, комментарии, замена текста) скрыты из bulk-профиля — они рабочие, но для длинной генерации не предлагаются.
3. **`format_range`** умеет только выравнивание + 4 символьных свойства; размер/цвет/шрифт/подсветка исключены (публичных геттеров для чтения нет).
4. `TOOL_UNCERTAIN` на любой записи останавливает прогон (по контракту, без автоповтора) — незавершённый вызов удерживает лок записи до перезагрузки плагина.
5. Оркестратор проверяет объём по `SymbolsWSCount` документа, а списки/заключение — эвристикой по фрагменту текста (2000 знаков); нераспознанная форма списка стоит одного лишнего прохода.
6. Нативные проверки записи возможны только на документах, которые создала сама R7 (минимальный собранный вручную DOCX читается, но в него нельзя писать).
7. Приёмочные прогоны в этой сессии **не доведены до 3×18 000** — остановлены владельцем вместе с задачей; последний фикс многострочных блоков проверен отдельно и успешно.

## 5. Целевой good-enough scope продукта (решение владельца)

- **Word:** 5–7 страниц за один свободный запрос — достаточно.
- **PowerPoint:** 3–4 слайда за один запрос — достаточно.
- **Excel:** типовые ежедневные сценарии — P&L, формулы, план-факт, таблицы, несколько связанных листов.
- **Не оптимизировать** продукт под 10/20/100 страниц Word, десятки слайдов или десятки Excel-листов без отдельной реальной потребности.

Примечание: инструменты агента для PowerPoint и Excel в этой стадии **не реализовывались** (стадия — Word + оркестрация); их good-enough scope выше зафиксирован как продуктовый ориентир для следующих стадий.
