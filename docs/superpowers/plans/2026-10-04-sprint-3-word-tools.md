# Sprint 3 — Word Tool Registry (план)

**Статус:** AUTHORIZED by direct user instruction (эта сессия). Код **не начат** — этот документ является предложением порядка реализации и ждёт подтверждения.
**Цель Sprint 3:** практически полезный Word Tool Registry для реальных пилотных задач — создавать и дополнять большие документы: главы, разделы, таблицы, списки, форматирование, ссылки, медиа.
**Критерий выхода Sprint 3:** агент по обычному пользовательскому запросу вида «создай структурированный документ примерно на 10 страниц, добавь главы, несколько таблиц, списки, выводы и оформи его» выполняет это **через Word Tool Registry без изменения Agent Runtime**.

## 1. Принципы (зафиксированы владельцем)

- Инструменты **пользовательского уровня и достаточно крупные**: одна операция = законченный осмысленный результат (глава, таблица, список), а не элемент разметки.
- **Не делаем:** микродекомпозицию вида `set_cell`; один `paragraph`/tool-call на каждый кусок большого документа, если блок можно безопасно вставить целиком; универсальный `do_everything`; отдельный большой research перед каждым инструментом.
- Каждый инструмент: **TDD → native verification на одноразовом документе → независимый review**.
- Если конкретный публичный R7 primitive не работает: зафиксировать **точный runtime FAIL** (API, сценарий, наблюдаемое поведение) → targeted поиск готового решения в официальной документации / GitHub / issues / плагинах → предложить рабочую альтернативу. **Не блокировать весь Sprint 3 одним инструментом**, если остальные реализуемы.
- Существующие инструменты `read_selection`, `insert_paragraph`, `replace_selection` **сохраняются как есть**, заново не реализуются.
- Agent Runtime (`src/agent/*`) **не меняется**: расширение идёт дескрипторами инструментов и плечами моста (`src/plugin/bridge.js` + UI-связка), как это предусмотрено расширяемым реестром.

## 2. Урок вставки, который становится общим правилом (уже доказан нативно)

Любая мутация обязана иметь **стратегию подтверждения**: наблюдение до отправки (baseline) и наблюдение после — через **доверенное публичное чтение**, и подтверждение только при однозначном изменении. Если подтвердить нельзя — исход **`TOOL_UNCERTAIN`**, прогон останавливается, лок держится, **повтора мутации нет**. Ложный успех недопустим; ложная неопределённость допустима. Для вставки это документный delta по декодированному тексту `GetFileHTML` (реализовано и проверено на Windows и на целевой Astra). Каждый новый mutate-инструмент в плане ниже называет своё наблюдение подтверждения.

## 3. Примитивы: что уже измерено, а что нет

| Семейство | Измеренный публичный primitive | Состояние |
|---|---|---|
| Чтение выделения | `GetSelectedText` | ✅ измерено, работает (Windows + Astra) |
| Чтение текста документа | `GetFileHTML` + разбор через `DOMParser` (текст с разделителями блоков) | ✅ измерено; используется подтверждением вставки |
| Предложение/слово на каретке | `GetCurrentSentence`, `GetCurrentWord` | ✅ измерено |
| Вставка текста | `PasteText` (пустой колбэк) + документный delta | ✅ измерено на обеих сборках |
| Замена текста | `SearchAndReplace`, `ReplaceTextSmart` | ⚠️ заявлены в SDK; **runtime не проверялись** |
| Комментарии | `AddComment`, `ChangeComment`, `RemoveComments` | ⚠️ не проверялись |
| Картинки | `PutImageDataToSelection`, `AddOleObject` | ⚠️ не проверялись |
| **Конструктор документа (таблицы/списки/стили/ссылки)** | объект `Api` внутри тела `callCommand` (наш пробник уже проверяет `typeof Api !== 'undefined'`) | ❓ **не измерено — ключевой вопрос Sprint 3** |

**Важное архитектурное наблюдение:** команда `callCommand` исполняет **наш авторский статический** код внутри редактора, и в этой области доступен объект `Api` (как builder-API в ONLYOFFICE-подобных редакторах: `Api.GetDocument()`, `CreateParagraph`, `CreateTable`, `CreateRun`, сеттеры форматирования и т. п.). При этом динамически сгенерированный/модельный код запрещён ADR — но статическое авторское тело на инструмент разрешено и уже используется адаптером. Это и есть вероятный маршрут для таблиц, списков, форматирования и ссылок.

## 4. Фаза 0 — матрица выполнимости примитивов (bounded, без фич-кода)

До реализации каталога выполняется **ограниченный набор проб** на живом редакторе (Windows 2026.3.1 + целевая Astra 2026.1.2.1942), результат — письменная матрица «примитив → есть/нет → точное наблюдение». Это не research, а измерения:

1. **`Api`-конструктор:** какие методы существуют (`GetDocument`, `CreateParagraph`, `CreateTable`, `CreateRun`, `CreateList`/`CreateNumbering`, `CreateHyperlink`, …), какие сеттеры форматирования доступны (`SetBold/SetItalic/SetFontSize/SetColor/SetAlignment/…`), и какие **чтения** доступны (`GetAllParagraphs`, `GetSelectedText`, `GetRange`, счётчики).
2. **Чтение структуры документа:** если структуру можно получить надёжно через подтверждённый публичный механизм — появится bounded structure read. Старый `read_context` на предположениях **не оживляется** (его primitive `GetDocumentStructure` отсутствует в обеих измеренных сборках).
3. **Замена:** реальный runtime-прогон `SearchAndReplace` / `ReplaceTextSmart` (в том числе поведение колбэка: bool или `undefined` — как это было с `PasteText`).
4. **Медиа:** `PutImageDataToSelection` / вставка изображения.
5. **Комментарии:** `AddComment` (неприоритетно).

Выход фазы 0: матрица + список семейств, где primitive отсутствует, с точным FAIL и предложенной альтернативой (по правилу владельца). Только после этого фиксируется окончательный состав инструментов. **Фаза 0 ВЫПОЛНЕНА — результаты в §9, окончательный состав в §10.**

## 10. Окончательный состав Word Tool Registry (по результатам фазы 0)

**Сохраняются без изменений:** `read_selection`, `insert_paragraph`, `replace_selection`.

| Порядок | Инструмент | Kind / policy | Основание (измерено) | Контракт результата |
|---|---|---|---|---|
| 1 | `read_document_text` | read / `auto` | §9 №1 | bounded/chunked; возвращает текст и признаки усечения |
| 2 | `read_paragraph` | read / `auto` | §9 №3 | текст каретки/сентенции |
| 3 | `find_text` | read / `auto` | §9 №4 | массив вхождений с ограничением |
| 4 | `read_structure` | read / `auto` | §9 №2 | заголовки/таблицы/секции/статистика; **заменяет отозванный `read_context`** |
| 5 | `insert_blocks` | mutate / `auto` | §9 №5,6 | создание массива блоков; подтверждение — readback (счётчики + markdown) |
| 6 | `insert_table` | mutate / `auto` | §9 №7 | `CreateTable` + заполнение; подтверждение — `GetAllTables()` + markdown |
| 7 | `set_heading` | mutate / `auto` | §9 №8 (`GetStyle`/`GetAllStyles` доступны) | подтверждение — readback стилей/структуры |
| 8 | `format_range` | mutate / `auto` | §9 №8 | bold/italic/font/size/color/alignment; подтверждение — readback |
| 9 | `add_hyperlink` | mutate / `auto` | §9 №9 | подтверждение — readback (markdown содержит текст и URL) |
| 10 | `replace_text` | mutate / `confirm` | §9 №12 | `doc.SearchAndReplace` + **обязательный** bounded readback |
| 11 | `insert_image` | mutate / `auto` | §9 №10 | `AddDrawing`; подтверждение — `GetAllImages()` |
| — | `create_list` | mutate / `auto` | §9 №11 — **эффект не подтверждён** | реализуется только после найденной рабочей формы; иначе отказ с точным FAIL |
| — | `insert_comment` | mutate / `auto` | пробник отложен | после основных инструментов, если нужен пилоту |

**Правило контракта результата (уточнено владельцем):** per-tool, а не универсально. Если публичный API даёт однозначный измеренно надёжный результат — используем его; если возврат ничего достоверного не сообщает (как `InsertContent` → всегда `true`, `SearchAndReplace` → `undefined`, `PasteText` → пустой колбэк) — bounded readback/delta; если надёжно подтвердить нельзя — `TOOL_UNCERTAIN`; automatic retry отсутствует всегда.

**Критерий выхода Sprint 3 не меняется:** пилотный запрос «структурированный документ ~10 страниц: главы, несколько таблиц, списки, выводы, оформление» выполняется через Registry **без изменения Agent Runtime** (на целевой среде).

## 5. Предлагаемый порядок реализации

> Этот раздел — первоначальное предложение. **Фактический состав и порядок — в §10**, скорректированные по измерениям фазы 0 (§9): гиперссылка и картинка подтверждены, `create_list` условен, `replace_text` требует readback, `read_context` заменяется измеренным `read_structure`.

### Фаза 1 — Чтение и навигация (все `read`, policy `auto`)
1. `read_document_text` — bounded/chunked чтение текста документа (`GetFileHTML` + разбор; параметры: `offset`/`maxBytes`/`scope`), **не** отправляет весь документ модели автоматически.
2. `read_paragraph` — текущий абзац/предложение на каретке (`GetCurrentSentence`; при необходимости через `Api`-чтение).
3. `find_text` / `search_text` — поиск с ограниченным числом результатов (чтение; мутирующий `SearchAndReplace` используется только в фазе 4).
4. `read_structure` — **только если** фаза 0 подтвердит надёжный публичный механизм (иначе не реализуется и не подменяется догадками).

### Фаза 2 — Создание и расширение (мутации, additive → policy `auto`)
5. `insert_blocks` (он же `insert_section`) — высокоуровневая вставка **нескольких связанных блоков**: заголовок + абзацы + подзаголовки одним вызовом (массив блоков, суммарный потолок по байтам), именно под запросы «добавь главу», «допиши раздел».
6. `insert_table` — таблица целиком: `rows`/`columns`/данные (2D-матрица) + опции заголовка; не ячейка за ячейкой.
7. `create_list` — список целиком (маркированный/нумерованный, уровни).

### Фаза 3 — Форматирование (мутации, `auto`)
8. `set_heading` — превратить блок в заголовок уровня N (если `Api` подтверждает стили).
9. `format_range` — форматирование диапазона/выделения: `bold`, `italic`, `font`, `size`, `color`, `alignment` и другие **реально подтверждённые** базовые свойства.
10. `add_hyperlink` — гиперссылка (текст + адрес) через подтверждённый `Api`-механизм.

### Фаза 4 — Редактирование
11. `replace_text` — поиск/замена по документу или заданной области (на измеренном `SearchAndReplace`); **policy `confirm`**, потому что операция разрушающая (в отличие от additive-создания). Существующий `replace_selection` остаётся отдельным confirm-сценарием.

### Фаза 5 — Медиа
12. `insert_image` — только если публичный R7 API подтверждён без отдельного большого research.

### Отложено
- `insert_comment` — после основных creation/editing/formatting инструментов, если действительно нужен пилоту.

## 6. Гейты и дисциплина (на каждый инструмент)

- **TDD:** RED-тесты на дескриптор, схему, precondition, обработчик и классификацию ошибок; полный suite не уменьшается; существующие тесты не ослабевают.
- **Native verification** на **одноразовом** документе: сначала Windows (быстрая петля), затем целевая Astra; для мутаций — подтверждение эффекта и отсутствие ложного отказа/ложного успеха.
- **Независимый review** каждого инструмента (read-only, со своими воспроизведениями) и закрытие всех условий.
- **Инварианты сохраняются:** закрытые схемы, потолки на payload/результат/действие, один диспатч мутации без повторов, документная стратегия подтверждения, `policy` на инструмент, отсутствие динамического кода в `src/`, аудит authored-кода и аудит бандла — зелёные.
- **Шлюз по примитиву:** нет работающего primitive → точный FAIL + targeted поиск альтернативы + предложение; инструмент может быть отложен, но Sprint 3 не блокируется.
- На каждый инструмент — атомарный коммит, затем обновление статуса.

## 7. Инфраструктура проверки (готова)
