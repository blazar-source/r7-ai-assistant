This Node standard-library server is **test infrastructure**, not a backend, proxy or product runtime. No production module imports it. The [build allowlist](../../../scripts/build-plugin.mjs) remains eight files and excludes this entire directory, test configuration, CA material and runtime state. No Node runtime dependencies are added.

## Parent-managed run, only after review/authorization

Run from the worktree: `node tests/acceptance/infrastructure/https-mock.mjs`. Importing the module does not start it. All inputs below except `R7_MOCK_CORS_MODE` are mandatory process environment variables; do not place concrete endpoints, certificates or private bytes in Git. The parent should explicitly set `R7_MOCK_CORS_MODE` for each measured run; omission defaults to `allow` only for backward compatibility. Use external paths or ignored temporary state. The CLI refuses port zero; host tests explicitly use an ephemeral port zero on IPv4 loopback.

The configured completion path is `{prefix}/v1/chat/completions`, HTTPS only. Settings must use the full authorized HTTPS endpoint ending in this path; no actual endpoint is baked in. The only accepted key is the deliberately **public, non-secret, synthetic** literal `PUBLIC-SYNTHETIC-TEST-ONLY`. Enter it only for this mock, never for a bank or real model. There is no configurable real-key override, upstream network access, model substitution or silent fallback. Foreign keys receive a constant 401 response without logging.

Only POST is accepted at the exact path (query variants rejected). Body has exactly `model`, `messages`, `max_tokens`, `temperature`; required headers exactly `Authorization`, `Content-Type`, `X-Session-ID` (UUIDv4). Ordinary browser/transport metadata headers are permitted; extra custom headers are rejected. Native tool/stream/response-format fields are rejected. Message order matches the [request snapshot interface](../../../src/shared/session.js): system, complete user/assistant pairs, optional separate user selection, current user. The `startMock` API requires the existing eight own enumerable configuration fields (`keyPath`, `certPath`, `listenAddress`, `port`, `prefix`, `profile`, `corsOrigin`, `delayMs`), with optional own enumerable `corsMode` and/or `sessionOrdinalLimit`. OPTIONS in **both** modes requires exact configured Origin, requested method POST and exactly the three required header names (case/order insensitive), replying204 only after validation. Mode A (`allow`) explicitly allows `POST` and `Authorization, Content-Type, X-Session-ID`, never wildcard credentials; an allowed Origin also receives exact CORS on POST/error responses as before. This is a positive **host-only** contract test. Mode B (`omit`) emits **no `Access-Control-*` headers at all**, including OPTIONS, accepted POST, same-origin/allowed-origin requests, validation errors, controlled errors, redirects, oversized and delayed responses. Body, route, authentication, UUID and resource validation remain identical in both modes; direct Node HTTPS can submit accepted POST in `omit` and is not a browser-security test.

A browser may block POST after missing-CORS preflight, or R7 CEF may relax security and actually send it. Host tests do not assert either outcome; the parent must measure actual CEF behavior without weakening TLS or security settings. Client CORS modes A/B remain **NOT RUN** until actual parent-owned target proof; host success cannot prove CEF's actual Origin/CSP/CORS handling.

`final` emits content-only closed JSON final; `proposal` emits content-only `r7_replace_selection` proposal with fixed synthetic replacement. Profile selection comes solely from trusted test configuration, never document instructions or content parsing for commands. `5xx` emits503, `oversize` emits an envelope larger than131072 bytes, `redirect` emits307 to the same completion path (client must refuse even same-origin redirects). Timeout delay must exceed the tested client deadline. Stop/cancel must abort the client; no retry is implied. Reconfigure only between parent-managed runs.

### Fixed diagnostics and measured literal Origin admission

Fixed aggregate Origin classes count **all requests before validation**, independently of configured origin: `originNullRequests` compares exactly with literal `null`, `originFileRequests` exactly with literal `file://`, `originMissingRequests` means absent, and `originOtherRequests` covers everything else (including empty values and nonliteral file origins). No parsing, copying, logging, persistence or hashing of Origin values occurs. Classification remains measurement only and never selects configuration. Trusted `corsOrigin` now also admits **only the exact literal `file://`**, alongside literal `null` and the existing exact HTTP(S) origin grammar. This is an Origin-header admission, not file endpoint transport: completion requests remain HTTPS only. Nonliteral file values (`file:/`, `file:///`, hosts/paths, wildcards, query/fragment) remain refused; request Origin must still equal the snapshotted configured value exactly. Configuring `file://` does not admit `null` or HTTP(S) request origins. In `allow`, matching requests echo exactly `file://`, never a wildcard; in `omit`, all `Access-Control-*` headers stay absent. No request chooses an origin, mode or profile.

`rejectedRoute`, `rejectedOriginMismatch`, `rejectedMissingOrigin`, `rejectedPreflightMethodMismatch`, `rejectedPreflightHeadersMismatch` count only the **first failing** relevant validator, in the existing order: exact route, present-origin mismatch, then OPTIONS missing origin, method, headers. They are not an exhaustive breakdown of all POST refusals, and simultaneous mismatches do not each increment rejection counters. Route comparison still uses exact `req.url`; query/encoded-prefix variants remain rejected. Missing Origin still permits an otherwise strict POST, never OPTIONS.

`preflightHeadersExact` / `preflightHeadersNonExact` count a boolean exact-name-set equivalence on OPTIONS reaching the existing preflight branch, using the unchanged case/order-insensitive comparison with exactly the three required headers. Missing, extra or duplicate names fail equivalence; no name/list is returned or retained. Earlier route/origin refusal leaves **both counters unchanged**, so zero does not prove a match. The reason counters and Origin classes distinguish the next actual client's rejection without widening the header whitelist or any CORS/TLS validator.

Parent-provided evidence from reviewed diagnostic mock `121d1aa` on Astra 1.7.9.41 / R7 2026.1.2.1942 measured one HTTPS OPTIONS, zero POST/acceptances, one literal-file Origin observation and one Origin mismatch, with all route/method/header counters zero. The configured literal `null` therefore mismatched the measured native literal `file://` before preflight-header validation. This bounded change admits that literal in trusted configuration only. Host regressions prove strict admission/validation and unchanged diagnostic contracts in both `allow` and `omit`; they do not prove that actual CEF will accept the response or send a validated POST. The parent must obtain fresh independent review before any copy, then run the separately authorized bounded native probes, collect only the closed technical snapshot, and retain `runtimeVerified=false` / Apply deny until independent runtime evidence. This change performs no VM copy, trust change or native probe. Host fixture checks current certificate validity on every start; cached parent-managed CA/leaf expiry and actual endpoint IP SAN/hostname verification remain parent checks, not claims based on this host fixture.
